## Executive summary

Choose the project, read its summary, and confirm the environment before changing anything. The deployment guide tells you which steps are automatic and which need an operator or a script. The troubleshooting guide records known failure modes so you can avoid repeating them.

## For a project owner

1. Open the overview to understand what exists and what is planned.
2. Read the deployment page to see how a change reaches preview, staging, or production.
3. Check verification limits before interpreting a documented host as a healthy live release.
4. Use the evidence links when a decision depends on a command, branch, or historical note.

## For an agent

### Establish the working context

Read applicable instructions from the workspace root down to the package you will touch. Confirm the canonical repository, remote, branch, working tree changes, and inspected revision. Local-only release helpers and task ledgers can carry facts absent from GitHub.

```powershell
git status --short --branch
git remote -v
git branch -vv
git rev-parse HEAD
```

Run these in the source repository selected by its overview. Do not reuse another project's commands because the service names appear similar.

### Plan the release path

Identify the target branch, deployment provider, database branch, configuration, and owner of each action.

| Question | Evidence to read |
| --- | --- |
| What triggers a build? | Workflow event filters and provider Git integration |
| Who creates a preview? | Preview scripts, workflows, and project instructions |
| What data does it use? | Neon branch creation and environment configuration |
| How is a stable host assigned? | Alias commands, provider settings, and release scripts |
| What proves readiness? | Revision signal, health checks, and affected browser journeys |
| Who cleans it up? | Resource ownership manifest and teardown procedure |

### Work, verify, and hand over

Use the project's required PR and preview lifecycle. Verify the actual deployment, record the tested revision, and remove only resources owned by the completed preview. A dispatch result proves a request was accepted; provider readiness and user-visible behavior require separate checks.

When a task changes deployment commands, fixes a recurring failure, or changes the branch/provider mapping, update this handbook with a source reference and inspection date.

## Troubleshooting the handoff

If instructions disagree, identify their dates and scopes and inspect the executable path that will run. Keep unresolved differences explicit. If credentials are unavailable, report which variable or loader is needed without printing secret values. Preserve provenance for local-only sources instead of inventing GitHub URLs.
